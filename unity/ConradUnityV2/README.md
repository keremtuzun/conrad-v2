# Conrad Unity V2 (simulator source tree)

Unity V2 is the vehicle-physics, sensor-viewpoint and mission-execution simulator of Conrad (spec ch20/ch21).
It owns robot physics, robot/environment interaction, sensor rendering and mission execution. It consumes the
shared scenario and never evolves twin (2T/2E/2S) truth.

> **Status: compiled, built and executed.** Editor **Unity 6000.5.9f1** (the project was upgraded from
> 2022.3.20f1; `ProjectSettings/ProjectVersion.txt`). The batch-mode compile has zero `error CS` and zero
> `warning CS`. `Assets/Conrad/Editor/BuildScript.cs` builds the headless Windows64 or macOS ARM64 player, and gate U0 is
> evidenced by `tests/unity_live` (see `docs/audits/U0_EVIDENCE.md`). All physical parameters are
> SYNTHETIC_ONLY, so the validity level is L1_APPROXIMATE_PHYSICS.

## Layout

```
Assets/Conrad/
  ConradUnityV2.asmdef                    core assembly, no third-party dependencies
  Core/                                   MiniJson, Vec3d/Quatd, ConradFrames (axis map), SeededRandom, SimClock,
                                          RobotConfigLoader (refuses OPEN parameters), validity levels
  VehicleDynamics/VehicleDynamics6Dof.cs  M nu_dot + C nu + D nu + g = tau + tau_env, applied as Rigidbody accelerations
  Hydrodynamics/HydrodynamicsModel.cs     linear+quadratic damping, added mass (+ Coriolis), buoyancy/weight at CoB/CoG
  Propulsion/ThrusterModel.cs             T = k u|u|, deadzone, saturation, asymmetry, latency, first-order lag, noise, faults
  EnvironmentInteraction/                 water density, surface, turbidity, currents; SceneGeometry (CONFIGURE_SCENE colliders)
  SensorSimulation/                       ISimSensor + SimSensorBase (acquisition vs delivery time), IMU, depth, camera, sonar
  RobotHardwareSimulation/                RHI server side: command validation, power model, health, state packets
  MissionExperimentRuntime/               ExperimentRuntime (fixed integer-ns stepping, seeds, deterministic reset),
                                          shared scenario loader, fault injector, JSONL replay logger
  ExternalInterfaces/Protocol/            BridgeProtocolHandler (wire protocol v1, CONTROL + TRUTH roles), FrameProbe
  ExternalInterfaces/Transport/           TcpBridgeServer (length-prefixed JSON over System.Net.Sockets),
                                          ConradHeadless (player entry point / watchdog), own asmdef, no DLLs
  Editor/BuildScript.cs                   builds Assets/Scenes/ConradHeadless.unity and a native standalone player
Assets/Scenes/ConradHeadless.unity        generated by BuildScript.SetupHeadlessScene
Examples/experiment.example.json          experiment config (format conrad.unity.experiment.v1)
```

The ZeroMQ server (NetMQ) was removed: its DLLs were never vendored, so it could not compile. The Python client
keeps an optional ZeroMQ transport for Python-side peers only.

## How the physics is applied

`VehicleDynamics6Dof` evaluates the full 6-DOF model in double precision in the Conrad body frame (+X forward,
+Y left, +Z up). It hands the resulting linear and angular accelerations to the Rigidbody with
`ForceMode.Acceleration`. PhysX only integrates and resolves contacts. `Rigidbody.linearDamping`,
`angularDamping` and gravity are disabled and sleeping is off (`sleepThreshold = 0`), so none of Unity's built-in
damping leaks in and a slowly drifting neutral vehicle is never frozen. Physics runs in `SimulationMode.Script`:
the runtime calls `Physics.Simulate(dt)` itself, driven by the bridge (lock-step) or by `FixedUpdate`
(free-running). The hull collider is a box of the RobotConfig `dimensions_m` on the Ignore Raycast layer, so the
vehicle never occludes its own sonar.

Documented L1 assumptions: dynamics about the body origin, diagonal inertia and added mass, and CoG offset
entering only through restoring moments. The same assumptions are made in `conrad.sim.kernel`.

## Building and running

1. Unity **6000.5.9f1** (Hub: `C:\Program Files\Unity\Hub\Editor\6000.5.9f1`). Batch mode works with the
   machine's entitlement license.
2. Build (from the repo root; about 1 min once `Library/` exists):
   ```
   "C:/Program Files/Unity/Hub/Editor/6000.5.9f1/Editor/Unity.exe" -batchmode -nographics -quit -projectPath unity/ConradUnityV2 -logFile unity/ConradUnityV2/Logs/u0_build.log -executeMethod Conrad.UnityV2.Editor.BuildScript.BuildWindows64Player
   ```
   The output is `Builds/Win64/ConradSim.exe` plus `Builds/Win64/conrad_build_info.json` (gitignored).

   On Apple silicon, build the native ARM64 player instead:

   ```bash
   /Applications/Unity/Hub/Editor/6000.5.9f1/Unity.app/Contents/MacOS/Unity -batchmode -nographics -quit -projectPath unity/ConradUnityV2 -logFile unity/ConradUnityV2/Logs/macos_arm64_build.log -executeMethod Conrad.UnityV2.Editor.BuildScript.BuildMacOSArm64Player
   ```
   Its executable is `Builds/macOS-ARM64/ConradSim.app/Contents/MacOS/ConradSim` (gitignored).
3. Run it from Python with `conrad.sim.unity.UnityPlayerSession` (it writes the RobotConfig export, the Scenario
   and the ExperimentConfig, picks free loopback ports and starts the player with `-batchmode`). By hand:
   `ConradSim.exe -batchmode -logFile player.log -conradRobotConfig robot_config.json -conradScenario scenario.json -conradExperiment experiment.json`.
   Do **not** pass `-nographics` when cameras are enabled: the camera sensor then refuses to start.
4. Gate U0: `python -m uv run pytest tests/unity_live -v -rA`.

The simulator reports its validity level in the handshake. With `configs/robot/sim_reference.yaml`, where every
value is SYNTHETIC_ONLY, it reports **L1_APPROXIMATE_PHYSICS**. L4 requires identified parameters plus a held-out
validation report, and Unity alone never claims it.

## Open items

- Twin 2S geometry -> `CONFIGURE_SCENE` wiring, and 2T/2E appearance hooks (integrator).
- Physical-parameter domain randomization and structured randomization inside Unity.
- Camera noise units: `noise_std` is interpreted as a fraction of full scale for RGB (documented, not measured).
- Camera rendering needs a GPU device; a host without one must run without camera sensors (the player refuses
  cameras under `-nographics`). No raycast depth-image fallback was needed on this host and none is implemented.
- Windows64 (Mono) is the original evidenced target. macOS ARM64 (Mono) is supported for native validation;
  other targets and IL2CPP are untested.
